# Private library PIN update

## Current behavior

The owner selected a simple six-digit PIN for their own use and deferred Claude
review. This update supersedes the earlier passphrase requirements in
`PRIVATE_LIBRARY_HANDOFF_20261127.md`; that earlier file remains as a historical
record of the initial implementation.

The product now shows a masked **Six-digit PIN** field with a numeric mobile
keyboard and an **Unlock collection** button. It accepts exactly six ASCII
digits. Leading zeros are significant and remain intact: credentials are
strings, never numbers. The form has no previous-passphrase mode or sharing
flow. The existing field identifier is retained for integration compatibility.

The low-level `unlockCollection(envelope, credential)` API also decodes old
collections with credentials admitted by the previous policy: 24–256
characters, no control characters and at least eight distinct characters.
This is decode compatibility only. `sealCollection(payload, pin)`, the CLI and
the product form all require six digits. A synthetic envelope generated by the
pre-PIN implementation verifies that compatibility without owner data.

## Preparing the owner's new encrypted collection

The actual owner secret, plaintext payload and ciphertext are outside this
change. The development worktree excludes the actual ciphertext file. The root
integration must reseal the unchanged payload with the new PIN before enabling
this PIN-only reader; an existing long-passphrase collection cannot be opened
through the new product form.

Keep both input files outside every Git repository. The PIN file contains six
digits, optionally followed by one LF or CRLF line ending. Leading/trailing
spaces and additional lines are rejected. On Unix it must be readable only by
its owner; use mode 0600. The output must be a new path.

```sh
node tools/private-library/seal.mjs \
  --input /outside-git/collection.json \
  --output /outside-git/collection-pin.enc.json \
  --pin-file /outside-git/private-pin.txt
```

Without `--pin-file`, the tool prompts twice in an interactive terminal with
echo disabled. The old `--passphrase-file` spelling is a deprecated filename
alias that also requires six digits; it cannot create another long-passphrase
collection. Supplying both file options is rejected. The equivalent JavaScript
entry point is `sealFile({input, output, pinFile})`.

There is no `--pin`, password-value argument or environment-variable secret.
Diagnostics do not echo credentials or plaintext. Existing encrypted outputs
are refused. A newly sealed output uses a fresh random salt and nonce.

## Privacy scope

A six-digit PIN has one million possible values and provides **casual privacy**
on this public static website. Someone who obtains the encrypted file can try
PINs offline. PBKDF2 slows each attempt but cannot make the PIN unpredictable
or impose a server-enforced retry limit. The interface states that limitation.
This setting is the owner's explicit convenience choice, not a claim of strong
protection for sensitive material.

AES-256-GCM, the 128-bit authentication tag, 128-bit salt, 96-bit nonce and
PBKDF2-SHA-256 at 600,000 iterations are unchanged. The exact authenticated
envelope and payload schemas, size limits and source metadata rules are also
unchanged. The app keeps its existing no-storage, no-history, no-telemetry,
plain-text rendering, automatic lock, in-flight cancellation and print
protections. Unlocking gives access to readable text that can still be copied.

JavaScript cannot promise physical memory erasure. A compromised hosting origin
can replace the HTML and script. No access accounts, individual revocation or
online lockout are added by choosing a PIN. No Claude review is asserted or
required to implement this owner-selected credential change.
