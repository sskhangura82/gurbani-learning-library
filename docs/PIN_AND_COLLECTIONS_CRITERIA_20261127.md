# PIN and complete-source collection increment

## Founder instruction

On 27 November 2026 the founder asked to continue building while away from the
desktop, use a simple PIN for the private collection, and queue actual Claude
review for later. This instruction supersedes the earlier long-passphrase-only
product choice. No new approval or Claude authentication is needed to build the
next development increment.

The chosen interface is a six-digit numeric PIN. Its low entropy provides casual
privacy for the current owner-only use. Keeping a public encrypted file does not
make a short PIN resistant to offline guessing. Preserve authenticated encryption
and the existing private-reader boundaries without overstating that protection.

The family deployment, saved reflections and production service worker remain
untouched. Builder tests use synthetic records. Historical publication still
requires the actual second source review; a queued review is not a completed one.

## PIN acceptance, before implementation

1. The default private UI accepts exactly six ASCII digits using a masked field
   and a mobile numeric keyboard. Leading zeroes are preserved; no numeric coercion.
2. New seals use the PIN policy. The owner PIN and plaintext stay outside Git;
   repository and logs receive no real PIN. The access instructions are replaced
   so the founder receives the current credential instead of a stale password.
3. AES-GCM authentication, random salt/nonce, the current KDF work factor, strict
   payload validation, SRI, lock-race prevention, automatic locks, no persistent
   private browser storage and public-cache exclusion remain intact.
4. Wrong/malformed PINs, tampered ciphertext and unsupported source data reveal
   no text. Public psychology and Sikh collections do not acquire a PIN prompt.

## Source collection acceptance, before implementation

5. Select only a named, pinned digital source whose original-text reuse terms and
   edition bibliography are actually inspected. Exclude modern translations,
   generated transliterations, commentary, audio and private comparative texts.
6. Do not promote the existing OpenGranth research packet merely by changing its
   `runtimeEligible` flag. It has no complete Shabad ownership map. Any new source
   uses its own explicit edition identity, metadata and admission record.
7. Original lines retain source IDs, order and exact text. If conversion from a
   legacy encoding is required, pin the converter and transformation, preserve
   source evidence, and refuse unsupported input rather than guessing a glyph.
8. The reader receives complete source-declared units. Selecting a page opens all
   its owning units in full, including lines on adjacent pages. Never infer a
   Shabad boundary from punctuation, an Ang number or a matching first line.
9. Page, section, group and author labels are metadata of the named edition.
   Keep absent or disputed metadata explicit. Byte verification establishes
   custody of this digital witness, not independent textual or historical truth.
10. Bind the root manifest, every content chunk, each unit's occurrence order and
    collection/edition identity. Missing, substituted, reordered or corrupt data
    refuses reading before source text renders. No cross-edition ID fallback.
11. Load only the required source data for normal navigation. URLs identify a
    collection, source page and optional exact unit/line; they carry no private
    reflection, PIN or inferred identity. Previous/next, direct page selection,
    Back/reload and an explicit reading-place resume must remain consistent.
12. Any new local reading-place record uses a separate exact source binding. It
    does not modify old reader records. A corrupt or stale record must not cause
    an invented resume destination or deletion of existing learning data.
13. Keep the existing ten-reader catalog, old source packs and saved-learning
    contracts stable. New complete-source readers are additional collection
    routes with their own source status and review scope.
14. Add new entry points to the complete HTML/script inventory. Rebuild changed
    closed bundles and their pins through exact new scope amendments; preserve
    all previous source-scope proofs. Do not place private assets in public cache.
15. Exercise actual complete source reconstruction and meaningful refusal cases,
    plus real browser navigation and narrow layouts using synthetic local state.
    Never claim physical iPhone/Safari acceptance from desktop emulation.
16. Prepare one exact-head review packet for actual Claude after the build. State
    source coverage, remaining source questions, tests and limits without waiting
    on Claude authentication to complete authorized development work.

## Completion claim

The deliverable is a tested development candidate with a simpler private entrance
and the source-backed collection work that the inspected evidence can support.
The candidate must identify actual coverage; a source-only edition reader is not
a completed translation, explanation, Santhiya or scholarly collation project.
